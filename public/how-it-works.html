How the system works

A guide to the architecture you have built — written so you can not only extend it, but explain it to someone who asks hard questions about it.

Start here: what you already have

The patient side of MediFlow is real software. Booking writes to a real database through real stored procedures, sign-in resolves a real role, and the permission rules are enforced by PostgreSQL rather than by hiding buttons. That is a meaningfully higher standard than most student projects and most production code.

What was missing was the other two thirds of the clinic — the doctor and the receptionist — plus the database foundation they need. This guide explains the whole system as it now stands: how the three roles connect, why the security is built the way it is, and how to add a screen.

The stack

  • Next.js 16 (App Router) + React 19 + TypeScript
  • Supabase — PostgreSQL, authentication, file storage
  • n8n — runs the “Ask MediFlow” assistant
  • CSS Modules with design tokens, no UI framework

The three roles

  • Patient books, checks appointments, shows a QR code
  • Reception checks patients in and out, runs the queue
  • Doctor consults, writes notes, sends follow-ups

The shape of the system

Four layers. Each one only talks to the one below it — that is what keeps the system understandable as it grows. 

   Browser  ·  patient / doctor / reception screens
      |                                    ^
      v                                    | live updates
   Next.js server  ·  role checks          |
      |                                    |
      v                                    |
   Supabase PostgreSQL  -------------------+
   row-level security · stored procedures

   Browser  - - - >  /api/mediflow/chat  ---->  n8n
   (chat only)       server-side proxy          assistant
                     holds the secret

Notice the dotted line. The browser never talks to n8n directly, and it never holds the n8n address. It calls your own server, which holds the secret and forwards only the message text — no name, no email, no login token, no medical information. If that webhook address leaked, anyone on the internet could trigger your workflows.

The rule this illustrates: a secret that reaches the browser is not a secret. Anything named NEXT_PUBLIC_* is visible to every visitor — view-source visible. Everything else stays on the server. This is why the chat goes through a proxy instead of calling n8n from React.

How permissions actually work

This is the most important idea in the codebase, and the one most likely to be asked about.

The weak way most apps do it

Hide the buttons a user should not have. The problem: hiding a button hides nothing. Anyone can open the browser console and call the same database that the button would have called. The data was never protected — only the path to it was decorated.

What MediFlow does instead

The database itself refuses. Every table has row-level security: a rule, written in SQL, that runs on every single query and decides which rows that particular user is allowed to see. There is no way around it, because it is not in the app — it is in PostgreSQL. 

-- A doctor may read an appointment only if it is theirs.
create policy appointments_select_doctor on public.appointments
  for select to authenticated
  using (private.is_doctor() and doctor_id = private.current_doctor_id());

So when a doctor's dashboard runs select * from appointments, it does not get the clinic's appointments and filter them in JavaScript. It gets only theirs — the other rows do not exist as far as that connection is concerned. A second doctor's account queries the same table and sees zero rows.

Where the role comes from

A role is read from the user_roles table, using the user's verified login. It is never read from a URL, a button, local storage, or user metadata — all of which the user could change themselves.

QuestionPatientReceptionDoctor
See their own appointments Yes All Own only
See another patient's appointment No Yes No
Read consultation notes No No Own only
Read allergies & medications Own No Own patients
Read a follow-up before approval No No Author
Change an appointment directly No No No

That last row is not a mistake. Nobody can write to the appointments table directly — not even reception. Every change goes through a stored procedure.

Reception cannot read clinical information. Not “the UI does not show it” — they have no database permission on consultation notes or follow-up instructions at all. If a receptionist opened the browser console and asked for them, they would get nothing back. That distinction — hidden versus impossible — is worth making if you are asked about privacy.

Why every change goes through a stored procedure

A stored procedure (Supabase calls it an RPC) is a function that lives in the database. The app cannot update an appointment; it can only ask the database to perform a named operation, and the database decides whether that operation is legal right now. 

-- Reception checks a patient in. Abridged from the real function.
create function public.staff_check_in_appointment(p_appointment_id uuid)
returns table (reference text, status text)
security definer set search_path = '' as $$
begin
  perform private.require_staff('reception');        -- 1. is the caller reception?

  select a.status, a.reference into v_status, v_ref
  from public.appointments a
  where a.id = p_appointment_id for update;          -- 2. lock the row

  if v_status not in ('scheduled', 'confirmed') then -- 3. is this transition legal?
    raise exception 'not_checkinable';
  end if;

  update public.appointments
     set status = 'checked_in' where id = p_appointment_id;
end; $$;

This buys four things that application code cannot reliably give you:

  • The rule lives in one place. Add a mobile app tomorrow and the same rules apply, with nothing to re-implement.
  • Steps cannot be skipped. Checking out a patient who was never seen is rejected by the database.
  • Double-clicks are harmless. The row is locked and the status re-checked, so the second click fails cleanly instead of corrupting anything.
  • Errors are named. not_checkinable is something the UI can turn into a sentence a receptionist understands. A raw database error is not.

security definer means the function runs with the database owner's permissions rather than the caller's — that is how it can update a table nobody can write to. That is also why the very first line re-checks who is calling. set search_path = '' closes a known attack where someone creates a fake table that a function picks up by accident, which is why every function name inside is written out in full.

The appointment lifecycle

One appointment travels through all three roles. This sequence is the spine of the whole product — the demo is simply walking it end to end. 

  scheduled --> confirmed --> checked_in --> waiting --> in_consultation
                                 ^             |               |
                              Reception     Reception       Doctor
                                                                |
                                                                v
                              checked_out <-- completed <-------+
                                   ^          Doctor
                                Reception

  branches:  confirmed --> cancelled       waiting --> no_show
  1. Patient
    Books an appointment and receives a QR code
    The QR contains only the booking reference — no name, no doctor, no medical information. If someone photographs it, they learn nothing about the patient.
  2. Reception
    Scans the QR, confirms identity, checks the patient in
    Identity confirmation is a deliberate separate step. A scanned code proves someone has the code, not that they are the patient.
  3. Reception
    Moves the patient into the waiting queue
    The doctor's dashboard updates at this moment, with no refresh.
  4. Doctor
    Reviews the summary, starts the consultation, writes notes
    Notes autosave as a draft while typing.
  5. Doctor
    Completes the consultation
    Behind a confirmation dialog, because it cannot be undone automatically. Only a doctor can make this transition.
  6. Reception
    Checks the patient out
    Only possible once the consultation is complete — the database enforces the order.
  7. Doctor
    Writes a follow-up and approves it
    Saving a draft sends nothing. Only Approve and Send makes it visible to the patient, and that gate is in the database, not the interface.

A note on completed. There is no separate “ready for checkout” status. An appointment that is completed but not yet checked_out is the ready-for-checkout list. Fewer states means fewer ways to get stuck — worth remembering when you are tempted to add one.

How a screen is built

Every screen in this codebase follows the same three-file shape. Once you have seen one, you have seen all of them. 

src/app/reception/queue/
  page.tsx           server component — checks the role, renders the client
  QueueClient.tsx    "use client" — fetches data, holds state, handles clicks
  page.module.css    styles scoped to this screen only

The server half

import { requireReception } from "@/lib/supabase/staff-auth";
import { QueueClient } from "./QueueClient";

export const dynamic = "force-dynamic";

export default async function Page() {
  const reception = await requireReception();   // redirects if not reception
  return <QueueClient displayName={reception.displayName} />;
}

This runs on the server, never in the browser. requireReception() checks the role and redirects if it is wrong — so by the time your component renders, the visitor is definitely a receptionist. You never write a permission check inside a component.

The client half

Anything interactive — state, clicks, effects — needs "use client" at the top of the file. It calls the ready-made functions in src/lib/staff/client-data.ts and never writes a database query of its own: 

const result = await checkInAppointment(appointment.id);

if (result.ok) {
  showToast(`${result.reference} checked in`);
} else if (result.reason === "not_allowed") {
  showToast("This patient cannot be checked in right now.");
} else {
  showToast("Something went wrong. Please try again.");
}

Every action returns a result object rather than throwing, and it never contains a raw database error. Database errors leak table names and column names to attackers, and mean nothing to a receptionist. Translating them into sentences is part of the job, not an afterthought.

Three states you must always build

Loading, empty, and error. Not optional: a screen that renders nothing while loading looks broken, and a screen that renders nothing when there is no data looks like it lost your information. StatePanel provides all three.

The rules the database will not let you break

These come from the clinical brief. They are enforced in SQL, so breaking one produces an error rather than a quiet mistake.

No clinical judgement, anywhere

No diagnosis, prescription, severity, urgency or triage exists in the schema. Statuses describe where the patient is in the building, never how ill they are. The assistant organises what a patient said; it never interprets it.

Nothing reaches a patient unapproved

A follow-up draft is invisible to the patient. Approval is an explicit, separate action by the doctor — and the permission rule, not the button, is what enforces it.

Status is never colour alone

Every status shows an icon, a text label and a colour. The app ships five colour-vision modes. A red dot alone is invisible to roughly one in twelve men.

Demo data says it is demo data

Prototype schedules and mappings are labelled on screen. In a clinical product, letting someone mistake invented data for confirmed data is a real hazard.

If you are asked

Questions worth being ready for, and honest answers.

How do you stop a patient from reading someone else's records?

The database refuses. Every table has a row-level security policy tied to the verified login, so a patient's query returns only their own rows. It is not enforced by the interface — if they bypassed our app entirely and queried the database directly with their own credentials, they would still get only their own data.

What happens if the receptionist clicks Check In twice?

Nothing bad. The stored procedure locks the row and re-checks the status, so the second call fails with not_checkinable and the interface shows a message. The appointment cannot end up in two states or skip a step.

Does the AI diagnose patients?

No, and it cannot. There is no diagnosis, severity or urgency field anywhere in the database to put such a thing in. The assistant matches what a patient describes to a clinic service and organises what they said for the doctor to read. Every doctor-facing summary is labelled as requiring review before clinical use.

Why is the doctor's login separate from the doctor's record?

Authentication and identity are different things. Supabase knows an email signed in; it does not know that email is Dr. Abbas. The doctors.user_id column links them, and every doctor permission resolves through that link. An account with the doctor role but no link can see nothing — which is the safe direction to fail in.

What is still missing?

Operational reports, the administrator modules, restricting staff sign-up to approved work emails, and the staff access-request flow. Doctor schedule management and reception's manual booking are partly built. Being straight about this is better than being caught out — a clear list of known gaps reads as engineering judgement, not as an excuse.
